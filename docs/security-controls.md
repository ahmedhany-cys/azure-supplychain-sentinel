# Security controls

| Area | Control | Where |
|---|---|---|
| Input validation | Strict pydantic schemas (`extra="forbid"`) for policies and release records; hex/length validation of digests and git revisions; enum-validated API parameters | `policies/model.py`, `core/release.py`, `api/main.py` |
| File handling | `resolve_within` confines every path after resolving symlinks; manifest discovery skips symlinks, `node_modules`, VCS and virtualenv directories; bounded walk depth and file count | `core/security.py`, `sbom/discovery.py` |
| Archives | Artifacts are hashed, never unpacked | `signing/verify.py` |
| Uploads | Size limits (`SENTINEL_MAX_UPLOAD_MB`), sanitised basenames, private 0700 temporary directory removed after use | `api/main.py`, `dashboard/views/trust.py` |
| Command execution | One runner: argv lists, `shell=False`, `stdin` closed, own process group killed on timeout, minimal allow-listed environment, stdout capped at 64 MB, stderr truncated and redacted | `core/runner.py` |
| Timeouts | Syft 120 s, osv-scanner 120 s, Cosign 60 s (configurable); version probes only after a tool has proven responsive | `config.py`, `scanners/osv.py` |
| Scanner output | Parsed with size limits; exit codes interpreted strictly; contradictory output is an error, never "clean" | `scanners/osv.py` |
| Secret redaction | PEM private keys, GitHub tokens, AWS keys, Azure connection-string keys and SAS signatures, `*_PASSWORD=`/`*_TOKEN=`/`*_SECRET=` assignments, bearer tokens; applied to tool stderr, reports, stored records; JSON kept parseable | `core/security.py` |
| Key handling | Dev keys: ECDSA P-256, PKCS#8 encrypted with `SENTINEL_SIGNING_PASSWORD`, created `O_EXCL` with mode 0600, never overwritten; errors never include key material; private keys refused as trust anchors; demo private key destroyed after fixture signing | `signing/keys.py`, `scripts/build_demo_fixtures.py` |
| Trust | Keys and builders only from policy; signature checked over actual digest; Cosign cross-check fails closed on disagreement; keyless bundles rejected as unsupported | `signing/verify.py`, `provenance/slsa.py` |
| Database | Bound parameters only; limit clamping; foreign keys; IDs validated by regex at the API | `storage/db.py`, `api/main.py` |
| API | Loopback bind by default, optional bearer token compared with `hmac.compare_digest`, `nosniff`/`DENY`/`no-referrer`/`no-store` headers, generic 500 messages | `api/main.py`, `api/__main__.py` |
| Dashboard | XSRF protection on, usage stats off, loopback address, every HTML interpolation escaped, repository-relative paths only | `.streamlit/config.toml`, `dashboard/ui.py` |
| Container | Digest-pinned base, checksum-verified tool binaries, hash-checked Python deps, non-root UID 10001, compose: read-only root FS, `cap_drop: ALL`, `no-new-privileges`, loopback port publishing | `Dockerfile`, `docker-compose.yml` |
| CI | `contents: read`, `pull_request` only, `persist-credentials: false`, SHA-pinned actions, `--require-hashes`, pinned and verified tool versions, weekly re-scan, no publishing | `.github/workflows/ci.yml` |
| Infrastructure | No admin user on ACR, Entra-only storage auth (shared keys disabled), RBAC Key Vault with purge protection, per-resource role scopes, OIDC instead of client secrets | `infrastructure/terraform/main.tf` |

## Dependency pinning and updates

- Direct dependencies use compatible-release ranges in `pyproject.toml`.
- Exact versions with SHA-256 hashes are in `requirements/requirements.txt` (runtime) and
  `requirements/requirements-dev.txt` (CI/dev), generated by `make lock` (uv).
- Update procedure: `make lock`, run `pytest` and `sentinel scan requirements`, review the diff of
  the lockfile in the PR (the Dependency review job checks new packages for advisories).
- Tool versions (Syft, OSV-Scanner, Cosign) are pinned in CI and the Dockerfile; bump them
  together and re-run `sentinel demo --check`.
- GitHub Actions are pinned to commit SHAs with the version in a comment; update via Dependabot or
  manually by resolving the new tag to its commit.

## Production signing guidance

The bundled key workflow is for development and demonstrations. For production:

1. Generate the signing key inside Azure Key Vault (`enable_signing_key_vault`); it cannot be
   exported.
2. Sign in CI with Cosign using the KMS URI from the Terraform output
   (`cosign sign-blob --key azurekms://<vault>.vault.azure.net/release-signing ...`), authenticating
   with GitHub OIDC (no stored secret).
3. Publish the public key (`cosign public-key --key azurekms://...`) into the policy's
   `signing.trusted_keys` through a reviewed change.
4. Consider keyless signing with Rekor transparency for public projects (roadmap).
